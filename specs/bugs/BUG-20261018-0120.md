# BUG-20261018-0120: `syauth pair` is unreachable in HEAD and its BlueZ numeric-comparison agent answers nothing — phone taps "Pair", nothing happens

## Summary

Two stacked defects on the desktop side of the pair flow, found while
reproducing the operator report "`syauth pair` → the desktop shows up in
the Android picker → the OS 6-digit dialog appears → I tap *Сопряжение* →
nothing happens":

1. **`pair` is not reachable in HEAD.** `crates/syauth-cli/src/main.rs`
   dispatches `list`, `revoke`, `status`, `install-pam`, `uninstall-pam`,
   `install-presenced`, `doctor` — there is **no `Pair` variant** and no
   `run_pair` call site anywhere in the workspace (`grep` below). The
   `syauth` binary built from this tree cannot pair at all. The operator
   is running `/usr/local/bin/syauth` (built 2026-05-21 12:20), which
   still carries the removed subcommand, which is why `syauth pair`
   appears to exist for them.
2. **Nobody installs the OS numeric-comparison handler.** The BlueZ agent
   in `pair_backend.rs::build_agent` resolves the operator's decision from
   `confirm_channel`, and `.unwrap_or(false)` when the channel is empty.
   `install_confirm_handler` has **zero production call sites** (definition
   + tests only). The channel is therefore always `None`, and every
   `RequestConfirmation` from BlueZ is answered `Err(ReqError::Rejected)`.
   The phone's LESC attempt dies, the bond never reaches `BONDED`, the phone
   never connects to the pair GATT service, the desktop's pubkey write never
   arrives, and `scan_peers` eventually reports `no advertising peers
   found`. The operator sees exactly "nothing happens".

The same regression explains the missing call site: the deleted `Pair` arm
of `dispatch` was the only place that built the backend *and* installed the
handler.

## Reproduction

- Method: live (Fedora BlueZ 5.87 + Samsung S25 Ultra `R5CY214FQHM`) +

- Steps (run "C", fully instrumented, 2026-10-18 00:55–01:00 MSK):
  1. `syauth pair --bond-dir /tmp/syauth-repro/C` (installed binary;
     daemon `syauth-presenced` running, as on a stock install).
  2. Phone: syauth → *Pair with computer* → CDM picker row "syauth" →
     OS pairing dialog shows code **495916** at 00:57:03.
  3. Tap *Сопряжение* at 00:57:53.

  `Bonded devices:` list contains no entry for `50:BB:B5:B9:93:AB` for the

- Evidence (desktop, earlier attempts at the same step):
  `bluetoothd[1179]: src/agent.c:simple_agent_reply() Timed out waiting for
  reply from agent` at 00:03:09 and 00:05:09 — an agent was registered and

- Evidence (mechanical, HEAD):

    green *because* the `pair` coverage rows were deleted with the

    `- [x] syauth pair prints adapter info, scans …`.
- Evidence (SPEC): §3.3 "IN — v0.1.0" — "`syauth pair` CLI that runs LE
  Secure Connections numeric comparison and shows a 6-digit OOB
  confirmation in the terminal"; §3.2 D5 — "LE Secure Connections numeric

## Expected Behavior

`syauth pair` exists in the shipped binary, and while it runs the desktop
answers the OS numeric comparison: it prints the 6-digit code, waits for
the operator's `y`/`N` (or the waybar click, or `--yes`), and replies to
BlueZ. On operator accept plus phone accept the phone reaches `BONDED` and
the pair GATT write lands.

## Actual Behavior

- HEAD: `syauth: unrecognized subcommand 'pair'`.
- Any build whose agent runs with an empty `confirm_channel`: the desktop
  rejects the numeric comparison without saying so, the phone silently
  falls back to `BOND_NONE`, and the CLI prints nothing until its 300 s
  advertise window expires (`error: no advertising peers found`).
- With the older installed binary the operator additionally sees a prompt
  (`BT pairing code: NNNNNN  Confirm on phone? [y/N]: `) that is flushed
  only when the process exits when stdout is not a tty, and that asks a
  question the operator already believes they answered on the phone.
  BlueZ's agent timeout then kills the attempt.

## Root Cause Analysis

One edit removed the `Pair` arm from `main.rs::dispatch` and with it the
only two production statements of the pair flow: constructing
`BluerPairBackend` and installing the operator's confirmation handler.
The suite stayed green because the subcommand's own coverage rows were
deleted in the same pass, so nothing failed. Because the agent's fallback
is *fail-closed rejection*, a missing handler does not look like a crash:
it looks like the radio silently refusing the user, which is why the
symptom was attributed to Bluetooth instead of to a dispatcher gap.

Secondary contributors captured during the same session (tracked below,
not fixed by this row):

- **`numeric_code: 0`** (`pair_backend.rs:465`): the real passkey stays
  inside the agent closure, so the terminal prints `BT numeric code:
  000000` and cannot satisfy "display matching code on both ends"
  (D5). `docs/known-gaps.md` DEV-001 closure evidence even records
  `BT numeric code: 000000` as "the LESC 6-digit code".
- **Two `request_default: true` agents.** `syauth-presenced`
  (`syauth-transport/src/peripheral.rs:375`) registers a default agent
  that *auto-accepts* every numeric comparison, and `syauth pair`
  registers its own while it runs. An always-on auto-accepting default
  agent contradicts §6 T-004 ("inbound bond requests are not accepted")
  and needs an explicit owner decision.
- **Phone-side CDM association accumulation.** `dumpsys companiondevice`
  held 19 associations for `com.sy.syauth.android` × `50:bb:b5:b9:93:ab`
  (ids 29–46), each pair attempt adding one; with an association already
  present CDM delivers presence events instead of a picker, so the run
  produced "no picker at all". Cleared with
  `cmd companiondevice disassociate 0 com.sy.syauth.android 50:bb:b5:b9:93:ab`
  (now 0). `RealCompanionAssociator.onDeviceFound` resumes success without
  launching the consent `IntentSender`, so nothing ever prunes them.

## Fix

1. Re-instate the `Pair` arm in `main.rs::dispatch`: build an ephemeral
   host `SigningKey`, construct `BluerPairBackend`, install the operator's
   confirmation handler, run `run_pair`, and surface `PairError` as today.
2. Make the handler installation *impossible to forget*: `PairBackend`
   gains `install_confirm_handler`, and `run_pair_with_io` installs the
   handler chosen by `PairOpts` (`--yes` → auto-accept, `--waybar` →
   waybar, otherwise stdio) before `scan_peers`. A caller can no longer
   reach the radio without an answer path.
3. Stop the silent reject: the stdio handler states where the keystroke is
   required and stops waiting after `PAIR_STDIO_DECISION_TIMEOUT` so the
   agent answers BlueZ with an explicit reject instead of hanging until
   BlueZ times out.
4. Report the truth: the agent records the passkey it was shown and
   `LescOutcome::numeric_code` carries it, so the terminal prints the real
   code.
5. Tests (added before the code, one behaviour each):
   `crates/syauth-cli/tests/cli.rs::pair_subcommand_is_reachable_and_documents_its_flags`,
   `crates/syauth-cli/tests/pair_flow.rs::pair_flow_installs_os_confirm_handler_before_touching_the_radio`,
   `…_yes_flag_installs_auto_accept_handler`,
   `…_default_opts_install_stdio_handler`,
   `pair_backend.rs::stdio_confirm_handler_rejects_when_no_answer_arrives`,
   `pair_backend.rs::recorded_passkey_reaches_lesc_outcome`.
6. Restore the deleted help-surface row for `pair` so a future removal of
   the subcommand turns the suite red by itself.

## Related observations (not fixed here; need a decision)

- Who owns the pairing agent — the CLI (`syauth pair`, per §3.3 + T-004)
  or `syauth-presenced`'s always-on auto-accept agent? The second option
  is what is deployed today and it contradicts T-004 as written.
- Whether the Android side must prune CDM associations (`removeAssociation`)
  before re-pairing, and whether `RealCompanionAssociator` should launch
  the consent `IntentSender` instead of resolving early.
